# Picking Logic v2

Status: **P6 complete — runtime cutover manually accepted**  
Target: post-0.0.4 development on `work`  
Runtime cutover: **not yet — current arrow generation remains transitional**

This document defines the next picking-engine design for TittyTatter. It exists to stop the Picking Guide from accumulating one-off fixes for individual patterns and to make the intended guitar-practice behavior explicit before another runtime rewrite.

The public UI may continue to expose only two simple strategies:

- **Экономный / Economy**
- **Переменный / Alternate**

Internally, v2 must model more than a sequence of `↓` / `↑` characters.

---

## 1. Why v2 is needed

The current picking code has already exposed several recurring problems:

- a repeated beat could change stroke directions only because the following beat changed;
- a Ramp stage could teach one pattern and then reverse it at a later stage;
- fixing Ramp stability by anchoring too aggressively could remove useful sweeps;
- generated inactive-beat TA pulses could restart as repeated downstrokes because OFF slots were treated as hard phrase breaks;
- stabilizing an identical beat by re-optimizing it in isolation could collapse useful phrase-level Economy behavior into ordinary alternate picking.

These are symptoms of one underlying issue:

> A pick stroke is not fully described by only `string + DOWN/UP`.

The engine also needs to understand continuity, string-change geometry, repeated motor patterns, Ramp identity, and the difference between a real rest and a training-generated placeholder.

---

## 2. Product goal

Picking Guide is a **practice aid**, not a shred-optimization benchmark.

The primary goal is:

> Suggest a technically sensible picking path that a guitarist can learn as a stable motor pattern.

A mathematically cheaper transition must not win if it forces the player to relearn an otherwise identical repeated figure for a tiny local advantage.

The v2 priority is therefore:

1. stable learnable motor behavior;
2. mechanically sensible string changes;
3. useful Economy sweeps;
4. deterministic, explainable output;
5. only then small local movement savings.

---

## 3. Terminology

### Attack

A sounding TI or TA event that receives an actual pick stroke.

### Slot

A rhythmic subdivision position. A slot may contain TI, TA, OFF, a covered long-note position, or a generated Ramp placeholder state.

### Real attack

An attack that comes from the user's stored pattern.

### Placeholder attack

A temporary attack generated by a Training Mode, currently most importantly the Ramp-mode TA pulse used on a not-yet-opened beat.

A placeholder is playable and needs a stroke, but it is **not** the same identity as the future real attack that will occupy that beat after the Ramp opens it.

### Stroke

`DOWN` or `UP`.

### String transition

A transition between two consecutive attacks on different strings.

Current TittyTatter mapping:

- TI -> string 5
- TA -> string 6

### Directional sweep

A same-direction adjacent-string transition that follows the physical direction of the pick:

- string 6 -> string 5 favors `DOWN -> DOWN`;
- string 5 -> string 6 favors `UP -> UP`.

This is not merely "two identical arrows". The transition should be represented internally as a linked sweep event.

### Motor motif

A repeating attack/rhythm unit that should normally retain the same stroke pattern on each repetition.

The motif may be a whole beat, multiple beats, or eventually a subdivision-level phrase that crosses beat boundaries.

### Phrase continuity

Whether two attacks belong to one picking phrase for optimization purposes.

OFF does **not** automatically mean "forget the previous stroke".

### Reset boundary

A point where the optimizer is allowed to forget prior stroke continuity and choose a fresh start direction.

### Escape profile

Future mechanical preference describing which stroke naturally escapes the string plane:

- AUTO / unspecified
- USX
- DSX
- DBX

The architecture must support this, but v2 does not require exposing it in the normal UI immediately.

## 4. Public strategy semantics

## 4.1 Alternate

The default user-facing Alternate strategy is **attack-alternate**, not ghost-stroke grid alternation.

Rule:

```text
attack 1: DOWN
attack 2: UP
attack 3: DOWN
attack 4: UP
...
```

Rests do not consume a direction.

Example:

```text
X . . . | X . . . | X . . .
DOWN      UP        DOWN
```

This is intentionally different from a continuous strumming interpretation where silent subdivisions may still consume invisible arm motion.

A future advanced option may add rhythmic/ghost-stroke alternate, but it must not silently replace the current user-facing Alternate meaning.

### Alternate invariants

- every consecutive **attack** flips direction;
- OFF consumes no attack direction;
- long-note covered positions consume no attack direction;
- generated Ramp placeholder attacks count as attacks;
- the same effective exercise always produces deterministic output.

---

## 4.2 Economy

The default user-facing Economy strategy is **practical directional economy**.

It is not "maximum possible sweeping".

Rules:

1. Same-string repeated attacks prefer alternate strokes.
2. Adjacent-string changes may use a same-direction sweep when the physical direction is correct.
3. A sweep must not be forced merely because one is locally available.
4. Repeated motor motifs should remain stable.
5. Already-learned real attacks in Ramp must not flip when later beats open.
6. Start direction is an optimization variable, not just a cosmetic downstroke preference.
7. OFF is interpreted through continuity semantics rather than automatically resetting the phrase.
8. Full-loop boundary transitions matter because practice is cyclic.
9. A tiny boundary gain must not override motif/stage stability.

This is deliberately a **practice-oriented** Economy mode.

---

## 5. What v2 must represent

The internal optimizer should work from normalized events rather than raw nested beat arrays alone.

Proposed conceptual event:

```text
PickingEvent
  slot_id
  beat_index
  subdivision_index
  source
    REAL_PATTERN
    RAMP_PLACEHOLDER
  state
    TI
    TA
    OFF
    COVERED
  attack
  string
    5
    6
    null
  phrase_boundary_before
  motif_id
  persistent_attack_id
  rhythmic_phase
```

A computed decision should contain more than one arrow:

```text
PickDecision
  stroke
    DOWN
    UP
    null

  transition_from_previous
    SAME_STRING
    ALTERNATE_CROSSING
    SWEEP
    RESET
    NONE

  sweep_group_id
  reason
```

The UI can continue to show only arrows initially, but this richer result prevents the algorithm from confusing a linked sweep with two unrelated same-direction strokes.

## 6. Picking state machine

At every attack, the optimizer conceptually tracks:

```text
PickerState
  previous_attack_string
  previous_stroke
  attacks_since_reset
  current_phrase_id
  current_motif_id
  string_travel_direction
  escape_profile
```

The state transition is evaluated from the previous attack to the next attack.

### Same string

Preferred:

```text
DOWN -> UP
UP   -> DOWN
```

Two same-direction attacks on one string are strongly discouraged unless a future explicitly modeled technique requires them.

### 6 -> 5

A continuing downstroke may form a directional sweep:

```text
6 DOWN -> 5 DOWN
```

### 5 -> 6

A continuing upstroke may form a directional sweep:

```text
5 UP -> 6 UP
```

### Wrong-direction same-stroke crossing

Examples:

```text
6 UP -> 5 UP
5 DOWN -> 6 DOWN
```

These are not valid directional Economy sweeps and should receive a strong penalty unless some future explicit technique mode permits them.

### Alternating string crossing

Examples:

```text
6 DOWN -> 5 UP
5 UP   -> 6 DOWN
```

These remain valid. Their relative desirability may later depend on inside/outside geometry and escape profile.

---

## 7. Continuity and rests

The current implementation has repeatedly suffered from treating every OFF as a hard reset.

v2 must distinguish **silence** from **picking reset**.

### OFF inside a rhythmic figure

Does not consume a stroke.

It also does not automatically erase previous picking context.

### Full real silent beat

May be a reset boundary when it represents an actual musical pause.

This should be an explicit continuity decision derived from the effective pattern, not an accidental consequence of flattening arrays.

### Ramp placeholder

A placeholder beat such as:

```text
TA . . .
```

means "one temporary attack on this beat", not "start a completely new phrase and default to DOWN".

Consecutive placeholder attacks must remain part of the temporary Ramp attack stream.

For example:

```text
TA... | TA... | TA...
DOWN    UP       DOWN
```

is a normal attack-alternate fallback when no sweep context changes it.

The first placeholder after an active phrase may instead continue a useful directional sweep.

---

## 8. Start polarity

The optimizer must evaluate both phrase starts:

```text
candidate A: starts DOWN
candidate B: starts UP
```

It must score the complete relevant phrase/cycle before choosing.

A downstroke start may remain the deterministic tie-break when candidates are otherwise equivalent, especially on a strong metric beginning.

It must **not** be a hidden assumption that prevents a better string-change path.

---

## 9. Parity

Attack parity matters because alternating strokes are a two-state system.

For each continuous same-string run, v2 should know whether the attack count is odd or even.

This affects which stroke reaches the next string change.

Example:

```text
2 attacks:
DOWN UP
next attack polarity is DOWN

3 attacks:
DOWN UP DOWN
next attack polarity is UP
```

Parity should be explicit optimizer information rather than an accidental emergent property.

Regression tests must include odd/even runs before both 6->5 and 5->6 transitions.

---

## 10. Inside / outside crossings

v2 should classify alternating string changes as inside/outside relative to stroke direction and string travel.

This classification is useful even before personalized escape mechanics are enabled.

The initial v2 implementation may use neutral/default costs, but the transition type must be available so later player profiles can alter the score without another architectural rewrite.

---

## 11. Escape mechanics hook

Picking mechanics are not completely described by arrow direction.

The architecture should reserve:

```text
EscapeProfile
  AUTO
  USX
  DSX
  DBX
```

Initial product behavior:

- default remains `AUTO`;
- no extra user-facing control is required for the first v2 implementation;
- AUTO must not pretend to know the player's actual motion.

Future behavior:

- USX can favor string changes after upstroke escape;
- DSX can favor string changes after downstroke escape;
- DBX can allow both-direction alternate crossings with lower penalty.

This is a scoring hook, not a requirement to diagnose the user's biomechanics.

---

## 12. Sweep groups

A sweep is a linked motion, so v2 should preserve that relation explicitly.

Example:

```text
TA(6) DOWN
          \
           sweep
          /
TI(5) DOWN
```

Internally both attacks may carry the same `sweep_group_id`.

Benefits:

- debugging can distinguish a real directional sweep from two unrelated DOWN strokes;
- regression tests can verify sweep intent directly;
- future UI may optionally draw a connector without redesigning the optimizer.

The first v2 UI does **not** need to visualize sweep links.

---

## 13. Repeated motor motifs

Stability rules must operate on motifs, not only on arbitrary optimizer positions.

### Required v2 behavior

```text
A A A
```

should normally use one stroke pattern for every A.

```text
A B A B
```

should normally preserve A and B identities.

A motif that crosses a visual beat boundary should eventually be detectable.

### Important rule

Do not obtain consistency by re-optimizing A in isolation after optimizing the full phrase.

That exact approach previously removed useful sweeps.

Instead:

1. detect motif equivalence;
2. represent repeated attacks with shared motif-relative variables or hard equality constraints;
3. optimize the complete phrase with those constraints active.

This lets phrase context and motif stability coexist.

---

## 14. Ramp: one joint optimization problem

Ramp must no longer be designed as:

> optimize stage 1, then optimize stage 2, then try to patch the differences.

Nor should it be:

> choose one arbitrary stage as the canonical truth and force every other stage to copy it.

v2 should solve all relevant Ramp stages as **one constrained problem**.

### Persistent attack identity

Every real stored-pattern attack receives a persistent identity.

If that attack exists in stage 1, stage 2, stage 3, and the final stage, its stroke variable is the **same variable** across those stages.

Therefore it cannot flip later.

### Placeholder identity

Temporary Ramp TA pulses are stage-local attacks.

They may have different directions between stages because they disappear or are replaced when the real beat opens.

### Joint objective

The solver considers:

- the final real bar;
- every Ramp stage that the user will actually practise;
- cyclic transition from bar end to bar start in every stage;
- persistent real-attack equality;
- motif equality;
- temporary placeholder transitions.

This directly captures the desired behavior:

> choose the best learnable scheme for the whole exercise, then reveal it progressively.

No "latest incomplete stage" heuristic should be required in the final v2 model.

---

## 15. Loop boundary

Loop practice is cyclic.

The transition:

```text
last attack of bar -> first attack of next bar
```

must be scored.

This includes:

- same-string alternation;
- directional sweep possibility;
- escape compatibility;
- turnaround;
- motif continuation across the boundary.

A solution that is locally perfect inside one displayed bar but awkward every time the bar loops is not optimal.

---

## 16. Turnarounds

A direction-of-travel reversal across strings is a meaningful event.

Example:

```text
6 -> 5 -> 6
```

must not be modeled as two unrelated pairwise transitions only.

v2 should tag a turnaround when string travel reverses.

The first implementation may simply add a modest transition cost, but the event must be explicit for future mechanics profiles.

---

## 17. Scoring model

Use **lexicographic priorities** where possible.

This is safer than trying to tune every musical rule into one fragile floating-point number.

### Priority 0 — hard validity

Never violate:

- attacks have exactly one stroke;
- OFF/COVERED have no stroke;
- strict Alternate alternates attacks exactly;
- invalid directional same-stroke string crossings are not labeled as sweeps;
- persistent Ramp real attacks retain one direction across stages;
- explicit motif-equality constraints are satisfied.

### Priority 1 — training stability

Prefer:

- identical repeated motifs use identical stroke patterns;
- already-learned Ramp attacks never change;
- phrase start polarity remains deterministic;
- avoid gratuitous reset/reorientation.

These should outweigh tiny local movement savings.

### Priority 2 — mechanical efficiency

Prefer:

- alternate strokes on the same string;
- valid directional sweeps;
- mechanically suitable string changes;
- fewer awkward turnarounds;
- future escape-profile compatibility.

### Priority 3 — rhythmic ergonomics

Prefer:

- sensible downstroke on a strong beginning when mechanically equivalent;
- stable cyclic bar boundary;
- reasonable parity into the next string change.

### Priority 4 — deterministic tie-break

When solutions remain equivalent:

1. DOWN at phrase/bar start;
2. lexicographically stable event order;
3. no random choice.

---

## 18. Scalar fallback weights

If the implementation uses one scalar cost internally, weights must preserve the priority ordering.

Illustrative scale only:

```text
hard-constraint violation       forbidden / infinity
Ramp persistent-stroke mismatch 10000
motif mismatch                  1000
same-string same-stroke         100
wrong-direction pseudo-sweep    100
awkward crossing                10
turnaround penalty              4
valid directional sweep         -4
neutral alternate crossing      0
downstroke start tie-break      -0.01
```

Exact numbers are implementation details and must be validated by regression tests.

The important property is the **orders of magnitude**, not these literal values.

---

## 19. Suggested solver architecture

The current code uses local dynamic programming plus post-processing.

v2 should move toward a constraint-aware solver over a small event graph.

A full bar is tiny, so exhaustive/DP state can remain practical.

Suggested layers:

```text
pattern/training state
        |
        v
normalize effective PickingEvents
        |
        v
detect identities / motif constraints
        |
        v
build stage/cycle transition graph
        |
        v
enumerate DOWN/UP decisions
        |
        v
score hard constraints + priorities
        |
        v
PickDecision[]
        |
        +--> current arrow UI
        +--> debug/explanation
        +--> future sweep visualization
```

Do not optimize GUI widgets directly.

`picking_logic.py` should remain a pure deterministic module.

---

## 20. Explainability

A future debug helper should be able to explain a decision in machine-readable form.

Example:

```text
slot 1.1 TA string 6 DOWN
  reason: phrase start tie-break

slot 1.2 TI string 5 DOWN
  reason: directional sweep 6->5

slot 1.3 TA string 6 UP
  reason: alternate crossing preferred over wrong-direction same-stroke crossing
```

This does not need to be shown to normal users.

It is intended for:

- regression debugging;
- screenshot investigations;
- future diagnostics;
- avoiding another cycle of guessing why one arrow changed.

## 21. Regression matrix

The v2 rewrite is not accepted until deterministic tests cover at least the following.

### Alternate basics

1. same-string attacks alternate;
2. TI/TA string changes do not break alternation;
3. OFF does not consume an attack stroke;
4. covered long-note positions do not consume a stroke;
5. Ramp placeholder attacks do consume strokes.

### Economy basics

6. same-string attacks prefer alternation;
7. 6->5 can form a `DOWN -> DOWN` directional sweep;
8. 5->6 can form an `UP -> UP` directional sweep;
9. wrong-direction same-stroke crossings are not classified as sweeps;
10. start DOWN/UP candidates are both evaluated.

### Repetition

11. `A A A A` keeps one A motor pattern;
12. `A A A REST` keeps one A motor pattern;
13. `A A A B` keeps one A motor pattern;
14. `A B A B` preserves A/B identities;
15. repeated motif at bar end/start remains consistent;
16. motif stability does not erase an existing valid sweep.

### Ramp

17. Ramp 1->2->3->4 keeps every previously opened real attack unchanged;
18. Ramp 2->full keeps the first two real beats unchanged;
19. placeholder TA pulses alternate as attacks when no sweep context changes them;
20. transition from active phrase into first placeholder may preserve a directional sweep;
21. opening a real beat removes/replaces placeholder identity without rewriting earlier real attacks;
22. full stage remains cyclic at the bar boundary.

### Parity

23. odd same-string group before 6->5;
24. even same-string group before 6->5;
25. odd same-string group before 5->6;
26. even same-string group before 5->6.

### Turnaround

27. 6->5->6 turnaround;
28. 5->6->5 turnaround;
29. turnaround across loop boundary.

### Silence / continuity

30. internal OFF slots do not reset attack parity;
31. real full silent beat may reset when explicitly classified as a reset boundary;
32. Ramp-generated `TA + OFF tail` does not reset every placeholder attack.

### Mixed rhythm

33. duplet -> triplet transition;
34. triplet -> sixteenth transition;
35. mixed-grid bar with cyclic boundary;
36. odd meters;
37. one-beat meter;
38. muted beat;
39. long-note coverage.

### Stability / determinism

40. repeated call returns identical output;
41. irrelevant UI state does not affect picking;
42. changing only a later unopened Ramp beat does not rewrite already-learned real attacks unless the joint global constraints genuinely require a different pre-training solution before the exercise starts.

## 22. Implementation phases

## Phase P0 — specification

This document.

No runtime behavior is changed merely by accepting P0.

## Phase P1 — normalized event model — IMPLEMENTED

Implemented on `work` without changing the current UI/runtime arrow path.

Current P1 primitives in `picking_logic.py`:

- `PickingEventSource.REAL_PATTERN`;
- `PickingEventSource.RAMP_PLACEHOLDER`;
- immutable `PickingEvent`;
- explicit `COVERED` slots;
- exact `Fraction` rhythmic phase;
- stable coordinate-based `persistent_attack_id` for real attacks;
- stage-local placeholder slots with no persistent attack id;
- explicit caller-controlled `phrase_boundary_before`;
- `normalize_picking_events(...)`;
- `normalize_ramp_stage_events(...)`.

Important P1 invariant:

> OFF is normalized as a rhythmic slot but does not automatically create a phrase reset.

Covered long-note beats are also represented explicitly instead of disappearing from the normalized stream.

P1 intentionally leaves `motif_id=None`; motif detection/constraints belong to P4.

The old UI/runtime path remains working and is not cut over by P1.

## Phase P2 — Alternate v2 — IMPLEMENTED

Implemented as a pure deterministic engine over normalized `PickingEvent` objects.

Current P2 primitives:

- `alternate_pick_events(...)` — one-to-one event-aligned decisions;
- `picking_directions_by_beat(...)` — compatibility projection back to the current UI beat/subdivision shape;
- `alternate_pick_beats_v2(...)` — normalization + Alternate v2 adapter for later integration.

Locked semantics:

- every attack flips direction;
- string changes do not interrupt alternation;
- OFF does not consume a direction;
- COVERED does not consume a direction;
- Ramp placeholder attacks do consume a direction;
- explicit phrase/reset boundaries do not restart public Alternate;
- explicit UP start is supported;
- invalid start input deterministically falls back to DOWN;
- identical inputs produce identical outputs.

The existing visual/runtime Alternate path is intentionally not cut over yet. P6 remains the integration checkpoint after Economy/motif/Ramp v2 behavior is ready.

## Phase P3 — Economy transition engine — IMPLEMENTED

Implemented as a pure event-based solver; runtime UI cutover remains deferred.

Current P3 primitives:

- `PickingTransition`;
- immutable `PickDecision`;
- `classify_pick_transition(...)`;
- `economy_pick_events(...)`;
- `economy_pick_beats_v2(...)` compatibility projection.

Implemented transition classes:

- `SAME_STRING_ALTERNATE`;
- `SAME_STRING_REPEAT`;
- `ALTERNATE_CROSSING`;
- `DIRECTIONAL_SWEEP`;
- `WRONG_DIRECTION_CROSSING`;
- `RESET`;
- `NONE`.

P3 behavior:

- same-string alternation is strongly preferred;
- valid 6->5 DOWN/DOWN and 5->6 UP/UP sweeps are explicitly recognized;
- wrong-direction same-stroke crossings are explicitly distinguished from real sweeps;
- DOWN and UP phrase starts are both searched;
- attack parity is exposed on every attack decision;
- OFF/COVERED do not reset Economy continuity;
- explicit reset boundaries are separate from silence;
- cyclic mode scores the real last->first attack transition;
- sweep-linked attacks share a `sweep_group_id`;
- every attack receives a machine-readable reason;
- deterministic tie-breaking keeps output stable.

P3 intentionally does **not** implement motif constraints or cross-stage Ramp equality. Those are P4/P5. It also does not infer USX/DSX/DBX.

## Phase P4 — motif constraints — WHOLE-BEAT STAGE IMPLEMENTED

The first P4 stage is implemented for repeated whole-beat motifs.

Current primitives:

- `annotate_whole_beat_motifs(...)`;
- deterministic whole-beat signature grouping;
- shared motif-relative attack variables;
- exact constrained Economy DP via `_solve_economy_constrained(...)`.

Behavior now covered:

- `A A A A` shares one A motor pattern;
- `A A A B` keeps one A motor pattern;
- `A B A B` preserves A and B identities independently;
- repeated A at visual bar end/start remains the same motif;
- OFF participates in motif shape without consuming attack parity;
- motif equality is enforced inside Economy optimization, not by rewriting arrows afterward;
- valid sweeps can survive motif stability when the full cyclic mechanics allow them.

The constrained solver retains only motif variables that must reappear later, so one-off attacks stay cheap in the DP state.

Subdivision-level motif detection that crosses beat boundaries is not implemented yet. Add it only if real patterns demonstrate that whole-beat motif identity is insufficient; do not block P5 merely to invent speculative motif cases.

## Phase P5 — joint Ramp solver — IMPLEMENTED

All requested Ramp stages now contribute to one optimization.

Implemented behavior:

- every real stored-pattern attack is represented once through its persistent identity;
- that real attack keeps one stroke across every Ramp stage where it exists;
- whole-beat P4 motif constraints remain active inside the joint solve;
- every stage contributes its own cyclic boundary cost;
- inactive-beat TA placeholders remain stage-local and are never promoted to persistent real attacks;
- placeholder chains are optimized as bridges between the last open real attack and the first real attack of the loop;
- when several equal-cost placeholder bridges exist, internal placeholder alternation is preferred over placing a same-string repeat between two temporary TA beats;
- covered beats create no placeholder attack;
- Ramp 1->2->...->full and Ramp 2->full use the same solver rather than separate anchor heuristics.

The implementation exploits Ramp's prefix structure: internal real-attack edges are weighted by how many stages contain them, while each stage boundary contributes a factor back to the first real attack. This keeps the joint solve exact without enumerating every persistent-stroke assignment.

The old transitional Ramp anchor/cleanup path remains in the runtime until P6 cutover and manual acceptance.

## Phase P6 — integration and manual acceptance — CUTOVER IMPLEMENTED

The live Picking Guide now uses Picking Logic v2:

- Alternate -> `alternate_pick_beats_v2(...)`;
- non-Ramp Economy -> `economy_pick_beats_v2(...)`;
- Ramp Economy -> `economy_pick_ramp_stages_v2(...)`.

The public two-strategy UI is unchanged.

The old transitional picking functions remain in `picking_logic.py` for regression comparison until local manual acceptance confirms the v2 runtime path. Do not delete them before that checkpoint.

Required local gate:

```bash
./tt check
./tt run
```

Manual acceptance must include:

- Loop / Economy;
- Loop / Alternate;
- Ramp from 1 beat / Economy across every stage;
- Ramp from 2 beats / Economy;
- Ramp / Alternate;
- repeated whole-beat motifs;
- the previously reported sweep cases;
- inactive Ramp TA placeholders alternating rather than restarting DOWN;
- already-open real Ramp attacks keeping the same stroke when later beats appear.

P6 is complete. Automated checks and the required live Loop/Ramp/Alternate manual acceptance were explicitly confirmed on the v2 runtime path.

## Phase P7 — optional advanced mechanics

Only after v2 is stable:

- USX / DSX / DBX profile;
- inside/outside preference tuning;
- optional sweep-link visualization;
- optional rhythmic/ghost-stroke Alternate mode;
- optional user start-stroke override if real practice shows a need.

These are not required for the first v2 cutover.

## 23. Migration rules

- Do not change root `VERSION` during the v2 development cycle.
- Keep `main` and published `v0.0.4` immutable.
- Work on `work`.
- Preserve the existing public UI unless a concrete v2 requirement demands change.
- Prefer pure functions and deterministic tests.
- Do not delete existing picking behavior until the replacement is test-covered.
- Avoid another sequence of pattern-specific conditionals.
- If a new screenshot reveals a failure, first add it as a regression case against this model.

---

## 24. Current-code relationship

The current post-0.0.4 picking commits remain useful evidence and regression material.

They should be treated as **transitional behavior**, not as the final architecture.

In particular, v2 should eventually replace the need for:

- post-hoc repeated-beat rewriting;
- stage-anchor heuristics;
- special cleanup of inactive Ramp TA pulses;
- ad-hoc fixes whose purpose is only to preserve one screenshot case.

The intended destination is one coherent optimizer whose constraints naturally produce those behaviors.
